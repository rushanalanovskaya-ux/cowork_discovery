# Приоритизация

## Два разных решения

**Что узнать следующим:** выбирать эксперимент, который снимает существенную неопределённость при малой цене и доступных данных. **Что разрабатывать:** выбирать среди достаточно проработанных возможностей с учётом обязательных ограничений, зависимостей и capacity.

Исходные P0/P1/P2 сохранены в `source_priority`; они не перезаписываются. `proposed_lane` — новая рекомендация для обсуждения. Утверждённый scope появляется только в decision record.

## Последовательность

1. Подтвердить риск: воспроизведение, влияние, частота, возможность обхода. Критичные безопасность/потеря данных — обязательный триаж, не соревнование по RICE.
2. Выбрать результат/сценарий и проверить доказательства. Wishlist и наличие у конкурента не являются demand evidence.
3. Проверить зависимости, альтернативы и уже реализованные части в SDD/Jira.
4. Получить оценки команды диапазоном; при неопределённости назначить техническое исследование.
5. Для сопоставимых кандидатов одного горизонта рассчитать RICE, затем проверить здравый смысл и capacity.
6. Записать решение, причины исключений и условие пересмотра.

## RICE: только при заполненных входах

`score = reach × impact × confidence / effort_person_weeks`

- reach: число подходящих пользователей/команд за один фиксированный период; единица должна совпадать у всех сравниваемых кандидатов.
- impact: ожидаемый эффект по общей шкале 0.25 / 0.5 / 1 / 2 / 3, определённой владельцем продукта перед сессией.
- confidence: 0…1, согласованная оценка качества evidence; не псевдостатистика из LLM-анализа интервью.
- effort_person_weeks: суммарные человеко-недели, >0. Команда уточняет диапазон, зависимости и риски; одно выбранное значение используется в расчёте.
- score_evidence: объяснение reach, impact, confidence, effort и горизонта со ссылками на расчёт/ревью.

Сейчас числовые входы намеренно пустые. `scripts/prioritize.py` показывает «недостаточно данных», а не подставляет нули или выдуманные оценки. Нулевой reach допустим и даёт нулевой score; отсутствие reach не равно нулю. Числовой score не переводит запись в Ready.

## Ритм управления — предложение

Еженедельный triage 30 минут: новые evidence, риски и дубликаты. Раз в две недели: выбор scope с Product/Design/Engineering/QA и Security по необходимости. После каждого эксперимента/релиза: обновление гипотезы и решения. Состав встреч можно адаптировать без изменения требований к трассируемости.
